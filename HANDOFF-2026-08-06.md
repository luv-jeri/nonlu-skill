## Hard-won lessons from this session — do not relearn these

**On writing evals (I got 11 wrong):**
- **Never point an eval prompt at live repo state.** "Check `src/Login.tsx`" in a markdown-only
  repo, or "absorb this skill's learnings" when there are none, tests the working tree at that
  instant, not the skill. The skill answers correctly and your test calls it a failure. **Paste
  the material into the prompt.** This bit 6 evals.
- **One observable behaviour per assert.** A compound assert ("keeps to the lite checklist AND
  names /qa-shield") fails correct work on its sub-clause. Bit 2 evals.
- **Prefer deterministic asserts.** A judge passed a reply with five lines of junk before the
  capsule, then failed a reply with none — same rule, opposite verdicts. Bit 2 asserts.
- **Interview-driven skills need their interview answered in the prompt.** skill-smith asks five
  questions before drafting; any assert about the *output* is untestable in one turn otherwise.
- **A red assert is not automatically a skill defect.** Read the transcript in `evals/runs/`
  first. Record which it was in `evals/eval-log.md`.

**On running evals:**
- They are **slow** — 10+ minutes per skill with judge asserts. Use `run_in_background: true`.
- **Never write a wait-loop that greps for `run_evals.py`** — the loop's own command string
  contains that text, so `ps | grep -c` never reaches zero and it waits on itself forever. This
  cost an hour. A check that cannot fail is not a check.
- `pkill -f` with a loose pattern killed two legitimate runs. Match on PID, not text.

**On verifying anything visual:** render it and look. Two real layout defects in the fake screen
(a stamp overlapping a heading, a clipped table value) were invisible from reading the code and
obvious in a screenshot.
